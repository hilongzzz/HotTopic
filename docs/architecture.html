01项目概述

GitTrend Hub 解决一个具体问题：GitHub 没有官方 Trending API，开发者想发现「正在升温」的开源项目缺乏可靠、结构化的数据源。本方案每日定时采集候选项目、记录 star 快照并计算真实日增量，经 AI 归类后以卡片流产品化呈现。

📡

🤖

规则预分类 + LLM 批量兜底，自动生成中文一句话简介，成本每天不足一分钱。

三个核心架构决策

决策一

前端不写 API 路由，RSC 直连 Supabase

全站只有读操作。Supabase 自带 PostgREST + RLS，服务端组件用 anon key 直查，配合 ISR 缓存。省掉一层自建 API，是独立开发者最快的路径。

决策二

AI 只处理「新项目」，且批量请求

池中 90% 是老项目，分类结果缓存在项目表永不重算。每天新增约 50–100 个项目，合并为 3–5 次批量调用（每次 20 个），AI 成本每天不到 1 分钱。

决策三

热度 = 每日 star 增量，靠自己积累

GitHub 查不到「今日涨了多少星」。每天把池内项目 star 快照写入 daily_trends，增量 = 今日 − 昨日。数据跑得越久，趋势图越有价值。

04数据库表结构

四张表各司其职：categories 是维度表，projects 存最新快照，daily_trends 是只追加的时序表，daily_rankings 是预计算的榜单物化结果。

create table categories (

  slug       text unique not null,          -- 'ai' / 'frontend' / 'backend' / 'devtools'
  name       text not null,                 -- 'AI / 机器学习'
  emoji      text,                          -- '🤖'（比 icon 字段简单）
  color      text,                          -- 主题色 '#8b5cf6'
  sort_order smallint not null default 100
);

  ('devtools',  '开发工具',       '🛠️', '#f59e0b', 4),
  ('mobile',    '移动开发',       '📱', '#ec4899', 5),
  ('database',  '数据库',         '🗄️', '#06b6d4', 6),
  ('other',     '其他',           '📦', '#6b7280', 99);

-- ══════════ 2. 项目表（核心实体，存"最新"快照） ══════════
create table projects (
  id               bigint primary key generated always as identity,
  github_id        bigint unique not null,      -- GitHub 仓库数字 ID，做幂等键
  full_name        text not null,               -- 'vercel/next.js'
  owner            text not null,
  name             text not null,
  description      text,                        -- 英文原描述
  summary          text,                        -- ★ AI 生成的中文一句话简介
  language         text,
  topics           text[] not null default '{}',
  homepage         text,
  owner_avatar_url text,
  stars            int not null default 0,      -- 最新 star 数（快照）
  forks            int not null default 0,
  open_issues      int,
  category_id      smallint references categories(id),
  category_source  text not null default 'ai',  -- 'rule' 规则 | 'ai' | 'manual' 人工纠正
  first_seen_date  date not null default current_date,
  updated_at       timestamptz not null default now()
);

create index idx_projects_category on projects(category_id);
create index idx_projects_stars on projects(stars desc);
create index idx_projects_topics on projects using gin(topics);

-- ══════════ 3. 每日热度趋势表（时序数据，只追加不更新） ══════════
create table daily_trends (
  id           bigint primary key generated always as identity,
  project_id   bigint not null references projects(id) on delete cascade,
  trend_date   date not null,
  stars        int not null,        -- 当日 star 总数快照
  stars_gained int not null,        -- ★ 当日新增 = stars - 前一日（预计算，免得查询时自连接）
  forks        int,
  unique (project_id, trend_date)   -- 幂等：重跑不会产生重复行
);

-- 首页核心查询：某天按涨星数排序
create index idx_trends_date_gained on daily_trends(trend_date, stars_gained desc);
-- 某项目趋势图
create index idx_trends_project_date on daily_trends(project_id, trend_date);

-- ══════════ 4. 每日榜单（物化结果，首页直接查，免实时计算） ══════════
create table daily_rankings (
  trend_date   date not null,
  project_id   bigint not null references projects(id) on delete cascade,
  rank         smallint not null,
  score        numeric not null,    -- 综合分：stars_gained 加权 + 新秀加成
  primary key (trend_date, project_id)
);

-- ══════════ RLS：匿名只读，写入走 service_role 绕过 RLS ══════════
alter table projects       enable row level security;
alter table daily_trends   enable row level security;
alter table daily_rankings enable row level security;
alter table categories     enable row level security;

create policy "public read" on projects       for select using (true);
create policy "public read" on daily_trends   for select using (true);
create policy "public read" on daily_rankings for select using (true);
create policy "public read" on categories     for select using (true);

设计要点

  • github_id 做唯一键 → upsert 幂等，Actions 重跑不脏库。
  • daily_trends 的 (project_id, trend_date) 唯一约束 → 同一天重复执行安全。
  • 首页查询只碰 daily_rankings（已算好分数和排名），join projects 取展示字段，单查询出全量卡片数据。
  • 时序表只追加、不更新，将来体积大了可按年分表或归档；500MB 免费额度足够跑数年。

05自动化采集脚本（GitHub Actions）

流水线共五步：候选发现 → 拉取详情 → upsert + 快照 → AI 归类 → 算榜 + 刷缓存。每天 UTC 2:00（北京时间 10:00）自动运行，也支持手动触发调试。

5.1 Workflow 定义

# .github/workflows/ingest.yml
name: Daily Ingest
on:
  schedule:
    - cron: '0 2 * * *'        # UTC 2:00 = 北京 10:00，抓前一天的完整数据
  workflow_dispatch: {}        # 支持手动触发，调试用

concurrency:
  group: ingest                # 防止两次运行重叠
  cancel-in-progress: true

jobs:
  ingest:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run ingest
        env:
          GITHUB_TOKEN: ${{ secrets.GH_PAT }}          # PAT，比 Actions 内置 token 限额高
          SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
          SUPABASE_SERVICE_KEY: ${{ secrets.SUPABASE_SERVICE_KEY }}  # ★ 仅在 Secrets 中
          AI_API_KEY: ${{ secrets.AI_API_KEY }}
      - name: Notify on failure
        if: failure()
        run: |
          curl -s -X POST "$SLACK_WEBHOOK" \
            -d '{"text":"🚨 GitTrend ingest failed"}'
        env:
          SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK }}
⚠️ 安全红线：service_role key 绕过 RLS，绝不能出现在前端代码或客户端可见的任何位置，只允许存放于 GitHub Actions Secrets 与采集脚本环境变量。前端一律只使用 anon key。

5.2 五步流水线（scripts/ingest.ts）

候选发现 —— 双查询互补

查询 A 抓近期创建的「新秀」黑马项目，查询 B 压住高星活跃项目保证榜单质量下限，按 github_id 去重合并。

拉取详情 + 幂等入库

对候选集逐个请求仓库详情（约 400 个请求，限额内绰绰有余），p-limit 并发 5 + 429 指数退避，upsert 进 projects。

记录每日趋势快照

写当日 daily_trends，stars_gained = 今日 star − 昨日 star；新项目无昨日数据时按首见日均摊兜底。

AI 归类 —— 规则优先，AI 兜底

规则映射先解决约 60%，剩余新项目按每批 20 个批量调用 LLM，强制 JSON 输出，低置信度归入 other 待人工纠正。

计算每日榜单 + 刷新前端缓存

综合分排序取 TOP 100 写入 daily_rankings，随后调用 revalidate 接口让用户下次访问即见新数据。

    .eq('project_id', projectId).lt('trend_date', today)
    .order('trend_date', { ascending: false }).limit(1).maybeSingle();

  await supabase.from('daily_trends').upsert({
    project_id: projectId, trend_date: today,
    stars: repo.stargazers_count,
    stars_gained: repo.stargazers_count - (yest?.stars ?? repo.stargazers_count),

06可靠性设计

无人值守任务的三个敌人：静默失败、数据写脏、外部服务限速。逐项对策如下。

风险对策
AI 挂了 / 超时分类失败不阻断流水线：降级到规则映射 → 再归 other，第二天自动重试
GitHub 限速请求间隔 + 429 指数退避；Search API 与 REST API 分开计数
数据写脏所有写入基于唯一键 upsert，workflow_dispatch 手动重跑无害
静默失败失败发 Slack / 飞书 webhook；每天跑完后校验 daily_rankings 行数 > 0
运行重叠Workflow 配置 concurrency 组，后触发者取消前一个
免费额度Actions 公共仓库无限制；每天约 2000 次数据库写入，远低于 Supabase 免费层
