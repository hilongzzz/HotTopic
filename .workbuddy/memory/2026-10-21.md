# 2026-10-21

## 修复 ingest 流水线 unique 冲突（idx_projects_full_name）

### 现象
CI 日报流水线失败：
`✗ ingest 失败: upsert projects 失败: duplicate key value violates unique constraint "idx_projects_full_name"`

### 根因
`projects` 表有**两个**唯一键，但 upsert 只声明了一个仲裁索引：
- `github_id`（唯一约束）— 仓库身份，GitHub 数字 ID 永不复用
- `idx_projects_full_name`（唯一索引）— 仓库地址，可变

`upsert(..., { onConflict: "github_id" })` 生成 `ON CONFLICT (github_id) DO UPDATE`，
只仲裁 `github_id` 索引。当同一 `full_name` 对应两个不同 `github_id` 时
（GitHub 上仓库删除后同名重建、或改名后旧地址被接管），
冲突落在 `idx_projects_full_name` 上 → 整批 INSERT 回滚。

已在真实 Supabase 上用合成数据精确复现（修复前必报同样的错）。

### 修复（scripts/ingest.ts ③ 步）
新增「地址归属消解」三步：
1. **③-1 本轮去重**：按 `full_name` 去重。同一地址多 id 时，
   ②池内刷新得到的（直接 GET 该地址当前主人）比 ①搜索索引权威；同源则取 star 更高者。
   同时过滤 full_name 不含 "/" 的非法记录。
2. **③-2 腾位**：库中占着本轮目标地址、但该地址本轮归属别的 id 的行，
   先改成 `vacated-<github_id>` 临时名让出地址。
   临时名不含 "/"，而真实 full_name 恒为 "owner/repo"，故永不冲突。
3. **③-3 清理**：腾位后其 github_id 仍未在本轮出现 → 仓库已消失，删除该行
   （daily_trends / daily_rankings 有 on delete cascade 连带清理）。

下游全部改用去重后的 `deduped`，避免 idMap 取到 undefined 写出脏快照。

### 顺带修的隐藏 bug
**② 池内刷新查询没分页** —— PostgREST 单次默认上限 1000 行，
而 projects 已有 1007 行 → 排在 1000 之后的存量项目永远进不了"需刷新"集合
（CI 日志"池内项目 1000"即为截断后的数字）。已改为 `.order("id").range()` 分页拉全量。
